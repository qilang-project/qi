# 多线程 FFI 重入 + qi_await 阻塞式异步桥

把 Qi 函数以 C ABI 导出成库后，**外部宿主的多个 OS 线程可以同时调用**这些
导出函数（反向 FFI 重入），并且能**阻塞等待 Qi 内部异步的结果**（qi_await 桥）。

本示例证明：**1000 个外部线程并发调 Qi 导出函数，零崩溃、结果全对、ARC 计数归零。**

## 文件

| 文件 | 作用 |
|------|------|
| `导出库.qi` | Qi 导出库：`累加`(整数)、`拼名`(字符串)、`异步计算`(未来<整数>)、`异步问候`(未来<字符串>) |
| `压测.c` | C 多线程压测驱动（1000 线程 × 数千次，整数+字符串+异步混合） |
| `压测.rs` | 等价的 Rust 多线程驱动（`extern "C"` 链接同一个库） |
| `构建并压测.sh` | 一键构建 + 运行（普通 / ASan / TSan） |

## 快速开始

```bash
# 先构建编译器与运行时（仓库根）
cargo build --bin qi          # qi 编译器
(cd qi-runtime && cargo build) # libqi_runtime.a

# 一键构建导出库 + C 驱动并跑 1000 线程压测
cd qi/示例/高级/多线程FFI
./构建并压测.sh
```

预期输出：

```
[qi-rc] 活跃对象=0 活跃字符串=0 活跃闭包=0
启动 1000 个外部线程：每线程 同步2000 次 + 异步100 次...
✅ 成功：1000 线程并发，共 4200000 次导出调用，整数+字符串+异步 结果全对，零崩溃
```

`活跃对象=0 活跃字符串=0 活跃闭包=0`（`QI_RC_REPORT=1` 打印）就是「无泄漏、
无 double-free」的直接证据：420 万次带字符串的导出调用后，ARC 引用计数精确归零。

## A. 外部线程执行模型：就地同步执行

外部线程第一次调用导出函数时，Qi 运行时已在**库加载**时由 `@llvm.global_ctors`
里的构造器自动 `qi_runtime_initialize()` 完成初始化（`Once` 幂等，单线程 dlopen
阶段跑完，早于任何外部线程调用）。

之后每个外部线程**就地同步执行函数体**——它不进 Qi 的 work-stealing 队列
（那是给 Qi 内部 `启动` 的 goroutine 的），就是普通地在自己的调用栈上跑 Qi
编译出来的机器码。这是最简单也最稳的模型：

- ARC retain/release 是原子操作（`AtomicI64` + AcqRel），多线程并发增减不错乱；
- 字符串/对象分配走 `std::alloc`（绕开全局锁），线程安全；
- 异常 frame 栈、profiler 递归深度等 **thread-local** 状态，外部线程首次进入时
  惰性初始化自己的那一份，互不干扰；
- 打印用「thread-local 行缓冲 + 单次 write_all」，多线程输出不撕裂。

### 导出函数里 `启动` goroutine 的影响

导出函数体内可以 `启动` goroutine——它会进 Qi 的 tokio 线程池后台跑。若导出
函数不等待就返回，goroutine 就 fire-and-forget（需 `等待协程` 显式 join）；若
等待，则外部线程阻塞等结果——这正好接上下面的 B。

## B. qi_await 阻塞式 ABI 桥

导出一个返回 `未来<T>` 的 Qi 异步函数时，编译器生成的 C ABI 包装会：

1. 调内部 Qi 函数 → 拿到 future 指针；
2. **阻塞** `等待`（`qi_future_await_*`）→ 取回 T 值；
3. free 掉 future 本体，把 T 按 C ABI 返回给 C。

于是 C 侧 `异步计算(21)` 直接同步拿到 `int64_t 42`，`异步问候("张三")` 直接拿到
`char* "异步你好, 张三"`——**C 无需理解 future，桥在包装里把它 await 掉了**。
外部线程在 await 期间阻塞的是它自己的线程（阻塞无害）；多个外部线程各 await
各自的 future，靠 A 的线程安全保证互不干扰。

生成的头文件里，异步导出函数的返回类型就是**解包后的标量**：

```c
int64_t 异步计算(int64_t x);   /* 内部是 未来<整数> */
char*   异步问候(const char* 名); /* 内部是 未来<字符串> */
```

## 明确砍掉：libuv / Go netpoller 零拷贝非阻塞联动

本次**不做**「对接外部事件循环（epoll/kqueue/IOCP）的 fd 就绪 → 协程唤醒」的
零拷贝非阻塞联动。那需要把 Qi 调度器的 waker 挂到宿主的 event loop 上、双向传递
fd 就绪事件，是多月的研究课题。这里只做**能真跑的两块**：线程安全重入 +
阻塞式 await 桥。阻塞桥对「C 调 Qi 异步函数、同步拿结果」这个最实用的跨语言异步
协同场景已经完全够用。

## Sanitizer 说明（诚实记录）

铁闸建议用 ThreadSanitizer 或 AddressSanitizer 跑一遍。实测在本机
（Apple Silicon + 较新 macOS）**ASan / TSan 运行时本身在进程启动阶段就死锁/崩溃**：

- ASan 卡在 `__asan::AsanInitInternal → InitializeShadowMemory` 的递归 malloc
  自旋锁里（`main` 都没进）；
- TSan 在影子内存映射阶段直接段错误。

这是 sanitizer 运行时与该 macOS 版本的已知不兼容，**与本代码无关**（同一 C 驱动
不加 sanitizer 跑 1000 线程完全正常）。因此把「无崩溃 / 无 double-free / 无泄漏」
的证据落在：

1. **1000 线程 × 4200 次 = 420 万次调用零崩溃、结果全对**；
2. **`QI_RC_REPORT` 显示 ARC 计数精确归零**（无泄漏、无 double-free 的直接信号）；
3. 运行时自带 `stdlib::rc_obj::concurrent_retain_release_is_balanced` 等
   多线程 ARC 单测（`cargo test` 全绿）。

在 sanitizer 可用的 Linux CI 上，`./构建并压测.sh asan` / `tsan` 可直接复用
（脚本已按 sanitizer 收敛线程/循环数以控影子内存开销）。
