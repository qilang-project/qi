# 运行时反射 + dlopen 插件热重载

面向 AI Agent 时代「prompt / 工具变了不用重启进程」的诉求。两块能力，都能真跑：

1. **运行时反射**：运行中的程序自省「当前有哪些中文函数 / 结构体 / 枚举」——
   内置 AI Agent 据此知道自己有哪些工具可用。
2. **dlopen 插件热重载**：运行中 `dlopen` 一个 Qi 编的工具动态库，调它导出的函数；
   工具升级后卸载旧版、加载新版，**同一进程内行为即刻切换，进程从不重启**。

> 明确砍掉「活协程跨 dlopen 迁移」（活栈里可能有指向旧 `.so` 的返回地址，属研究级危险）。
> 本示例只做同步插件函数的加载 / 调用 / 卸载 / 换版，全部能真跑。

## 文件

| 文件         | 说明                                                            |
| ------------ | --------------------------------------------------------------- |
| `主程序.qi`  | 主进程：先反射自省自己的函数 / 结构体，再热加载插件 v1 → 换 v2  |
| `插件v1.qi`  | 插件 v1：`导出 处理(x)=x*2`、`导出 问候(名)="v1 你好, "+名`     |
| `插件v2.qi`  | 插件 v2：同名符号，`处理(x)=x*3`、`问候` 前缀 "v2"（行为升级）  |
| `运行.sh`    | 一键复现：编两个插件动态库 → 运行主程序                          |

## 一键运行

```bash
cd qi/示例/高级/热重载
QI_BIN=../../../../target/release/qi ./运行.sh
```

预期输出（节选）：

```
========== 运行时反射自省 ==========
用户函数数量: 2
  相加 : 整数, 整数 -> 整数
  问候 : 字符串 -> 字符串
有函数 问候? 是

========== dlopen 插件热重载 ==========

v2  问候("齐") = v2 你好, 齐

同一进程内 处理(21): 42 → 63；问候: v1 → v2。行为已切换，进程从未重启。
```

## 反射 API（`导入 标准库.反射;`）

| 调用                       | 返回          | 说明                             |
| -------------------------- | ------------- | -------------------------------- |
| `反射.函数数量()`          | `整数`        | 用户函数个数                     |
| `反射.函数名(i)`           | `字符串`      | 第 i 个用户函数名                |
| `反射.函数签名(名)`        | `字符串`      | 某函数的 "参数..., -> 返回" 文本 |
| `反射.函数列表()`          | `数组<字符串>`| 所有用户函数名                   |
| `反射.有函数(名)`          | `整数`(1/0)   | 是否存在某函数                   |
| `反射.结构体列表()`        | `数组<字符串>`| 所有结构体名                     |
| `反射.结构体字段(名)`      | `字符串`      | "字段:类型, ..." 描述            |
| `反射.枚举列表()`          | `数组<字符串>`| 所有枚举名                       |

元数据由编译器在 `main` 序言里自动登记（用户 `入口()` 体运行之前），无需手写。
登记范围是用户定义的函数 / 结构体 / 枚举（不含 `入口` 自身与 `外部` C 函数），
函数按名字排序保证跨运行输出确定。

## 插件 API（`导入 标准库.插件;`）

| 调用                              | 返回     | 说明                                   |
| --------------------------------- | -------- | -------------------------------------- |
| `插件.加载(路径)`                 | `整数`   | dlopen，返回句柄（0 = 失败）           |
| `插件.取函数(句柄, 符号名)`       | `整数`   | dlsym，返回函数指针（0 = 失败）        |
| `插件.调用整数(函数指针, 参数)`   | `整数`   | 调用 `(整数)->整数` 签名的插件函数     |
| `插件.调用无参整数(函数指针)`     | `整数`   | 调用 `()->整数`                        |
| `插件.调用字符串(函数指针, 参数)` | `字符串` | 调用 `(字符串)->字符串`                |
| `插件.卸载(句柄)`                 | `整数`   | dlclose                                |
| `插件.错误()`                     | `字符串` | 最近一次 dl* 错误文本（诊断用）        |

句柄 / 函数指针以不透明整数（64 位指针位模式）表示，不入 ARC、不解引用。

## 插件 = 反向 FFI 动态库

插件就是用 `导出 函数`（反向 FFI）编出来的动态库。用显式 ASCII C 符号名，
主进程 `dlsym` 按这些名字取函数：

```qi
包 工具一;
导出 "chuli" 函数 处理(x: 整数): 整数 { 返回 x * 2; }
导出 "wenhou" 函数 问候(名: 字符串): 字符串 { 返回 "v1 你好, " + 名; }
```

```bash
qi compile --库 动态 插件v1.qi -o 工具v1.plugin   # mac .dylib / linux .so，扩展名随意
```

> 两个插件用了不同包名（`工具一` / `工具二`）——同目录同包名的 `.qi` 会被当作
> 同一模块合并，导致 C 导出符号重名。不同包名各自独立成库。

## 双运行时问题：为什么不会「两个 ARC 堆打架」

主进程静态链一份 `qi-runtime`，每个插件 `.so` 也各自打包一份（`--库 动态` 用
`force_load`）——进程里因此有多份运行时副本。这**不会**互相打架：

1. **同一个分配器**：`qi-runtime` 无自定义 `global_allocator`，所有副本都用系统
   `malloc/free`，同一 libc 堆。
2. **引用计数内嵌在分配头**（magic + refcount，见 `rc_obj` / `qi_str`），不是某个
   中央堆登记表；各副本 header 布局与 magic 完全一致。
3. **初始化不起线程**：`qi_runtime_initialize` 用 `Once` 幂等，且只建内存 / IO 管理器，
   **不**启动调度线程（异步调度器是首次用到才惰性起 tokio）。故插件的
   `global_ctors` 自初始化后没有指向该 `.so` 代码的活线程 / 未返回协程栈 ——
   `dlclose` 卸载安全（这正是「活协程跨 dlopen 迁移」被砍掉的危险点，此处规避）。

更关键：**字符串调用边界只走 C 字符串**。`插件.调用字符串` 把主进程 Qi 串当只读
`char*` 借给插件（插件内部 `qi_string_from_cstr` 拷成自己副本的 Qi 串）；插件返回它
`strdup` 出来的 **C 堆串**，主进程再 `qi_string_from_cstr` 拷成自己副本的 Qi 串后
`free` 掉那个 C 串。于是**没有任何 Qi RC 对象跨越 `.so` 边界**——每条 Qi RC 串都在
「分配它的那份副本」里创建与回收，跨边界的只有 libc 管的 C 串。无 UAF、无双重释放、
无跨副本 refcount 竞争。

用 `QI_RC_REPORT=1` 跑主程序，主进程与两份插件副本退出时各报 `活跃对象=0 活跃字符串=0
活跃闭包=0`——三方全零，无泄漏。

## Linux 提示

把 `../../../../target/release/qi` 换成你的 `qi` 路径即可。插件扩展名无所谓
（`dlopen` 不看扩展名），脚本统一用 `.plugin`。
